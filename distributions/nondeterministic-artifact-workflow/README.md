# Nondeterministic Artifact Workflow

An optional package for a person who uses AI to make visual or other binary
artifacts from their own source files, then decides which exact result to keep.
**New to this workflow? [Start here](start-here.md).** The guide walks through
setup, a first job, review, and approval in ChatGPT Work. The reusable pieces
are the [task contract](task-contract.md) and [Work launcher](work-launcher.md).
The [Dowsing Rod example](examples/dowsing-rod.md) shows one photo pilot; its
editing choices are examples, not general rules.

This distribution owns these copyable templates and its folder convention. It
does not own Playbook doctrine, a storage account, an image generator, or a
production approval policy. Its boundaries derive from
[`core-model.md`](../../docs/core-model.md) and the accepted, **opt-in**
[`v2-architecture-foundation.md`](../../docs/v2-architecture-foundation.md),
especially exact candidate and decision applicability. The current v1/default
bootstrap stays unchanged. Using this package does not claim that a v2 runtime
or storage connector has been qualified.

## Set up your own workspace

Connect a durable store you are authorized to use to your Work environment.
Choose a root folder in **your** account and provide that root, the store name,
and the completed task contract when launching a run. Confirm that the Work
session can read original binary files and create, read back, and move files in
that root. Check your own privacy, retention, client, and publication rules
before sending source material to any generation provider. A storage link,
preview, or filename alone is not the source binary.

Suggested paths are relative to that chosen root:

```text
01 Sources/<task>/              original inputs; do not overwrite
02 Contracts/<task>.md          the current task contract
03 Candidates/<task>/          unique, immutable attempts and finishing derivatives
04 Accepted Masters/           exact human-approved master
05 Review Notes/<task>.md       choice, reasons, exact identities, and approval
```

The numbers only keep the folders easy to scan. An existing folder layout is
fine if the contract maps each state to its actual folder. Store identity
should include the provider's file identity or version plus a byte digest when
the route can verify one; names and paths are useful locators, not sufficient identity. Keep
the source and approved master recoverable under your storage policy.

## Run boundary

1. The human supplies the task contract and exact source identities, states
   protected truth and acceptable variation, and authorizes the bounded run.
2. Work stages the exact source binaries from the connected store, generates
   new candidates without overwriting earlier attempts, saves them to the
   candidate folder, and verifies the saved objects as far as its route allows.
3. Work stops. The human reviews the actual candidates against the contract
   and any real-world subject. Selection of a promising candidate is not final
   approval or publication permission.
4. If selected, Work may apply only the deterministic finishing steps the
   human authorized, save a new derivative, and verify its mechanical output.
   Any semantic edit or new generation creates a new candidate for review.
5. The human approves the **exact final file** for the stated use. Only then
   may Work move that same verified file into Accepted Masters and read back
   the resulting identity. A move must not silently replace existing content.
   Record a changed provider identity or path with byte continuity; if
   continuity cannot be verified, hold for review. Publication remains a
   separate decision.

Input replay preserves the request and source identities; it does not promise
identical generated bytes. Acceptance applies to the actual output, contract,
and intended use, not to its prompt, predecessor, or sibling. This is a
portable operating pattern, not an automated approval system.
